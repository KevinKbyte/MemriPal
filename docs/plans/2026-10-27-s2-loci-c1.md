# C1 decision (SUP-011): MemriPal S2 Loci request shape

Unit: s2-loci. Phase: /sdlc Brainstorm -> C1. Plan draft: docs/plans/2026-10-27-s2-loci.md.
Restated task: one uploaded photo -> server-validated processed image + <= 12 route-ordered loci (Spark phrases ->
SAM per phrase -> area/IoU/spacing/duplicate filters -> A5 re-ask -> route order), in `fixture` mode offline and
`meta` mode live, behind a minimal upload UI. The choice: where orchestration lives and how live calls reach Meta.

## Approach A (RECOMMENDED): one synchronous `POST /loci`, ModelBackend widened with keyword request fields

- Problem: the client must get loci from one photo while D5 keeps the server stateless and the Ledger forbids an
  open model proxy; today `ModelBackend.segment/spark_json` take only a sha, so `MetaBackend` cannot call Meta.
- Solution: one endpoint takes raw image bytes, runs `process_upload` -> `find_loci` server-side (thread pool for
  SAM), returns processed image + loci; `segment`/`spark_json` gain keyword-only `image_jpeg`/`prompt`/`schema`
  that FixtureBackend ignores and MetaBackend requires; write-through stays in MetaBackend (after item 5).
- Tradeoff: no per-phrase progress (one spinner for possibly tens of seconds); widens the backend Protocol that the
  held cache-key fix also edits, so item 5 must land first.
- Worst case vs today: today there is no loci path at all; worst case the request is slow (SAM latency unmeasured)
  and Kev waits on a spinner, or item 5 slips and S2.3/S2.6 wait while S2.1/S2.2 still land.

## Approach B: client-orchestrated steps (`POST /phrases`, `POST /segment` per phrase, `POST /select`)

- Problem: same as A, plus showing per-phrase progress while SAM runs.
- Solution: browser calls Spark once, then fires SAM requests per phrase itself (re-sending the photo each time),
  then posts all boxes to a pure selection endpoint; re-ask is a second client round.
- Tradeoff: live progress UI, but 3 endpoints, the photo re-uploaded ~25-50 times per run, client holds pipeline
  logic (harder to test, two languages), and `/segment` is a per-phrase SAM proxy -- exactly the "open model proxy"
  the round-1 Ledger (S2) rejected; each endpoint needs its own caps and later its own passcode/budget.
- Worst case vs today: a public `/segment` becomes a free SAM relay for any phrase, and spend multiplies with
  upload count; more surface to harden before S7.

## Approach C: one `POST /loci`, separate provider ports outside ModelBackend

- Problem: same as A, without touching the ModelBackend Protocol the held fix is editing.
- Solution: new `PhraseSource` and `Segmenter` ports in loci.py (meta, modal, fixture implementations), each with
  its own caching wrapper; ModelBackend keeps only its S0 shape.
- Tradeoff: zero collision with item 5 today, but two cache/replay layers (ModelBackend for S3/S4, ports for S2)
  and duplicated write-through/fixture logic; item 5's key rules would need applying twice.
- Worst case vs today: fixtures recorded by two caches drift apart; S3/S4 inherit the inconsistency or a later
  merge of the two layers costs a day in a 6-day schedule.

## Recommendation

A. It is the smallest surface that satisfies D5, the Ledger's no-open-proxy rule and one replay layer (D3). The
collision with item 5 is real but is a sequencing fix (item 5 first), not a design flaw; S2.1 (image intake) and
S2.2 (pure locus selection) are collision-free and start now.

## Decision (2026-10-26)

Kev approved after a 5-adversary eval (root problem; defenders of A, B, C; framing-rejector).

- Chosen: **A-prime** (A refined). One synchronous `POST /loci`. The `ModelBackend` Protocol takes a frozen
  `ModelRequest(method, image_jpeg, subject, attempt, model, prompt_template_id, gen_params, schema)`; `CacheKey` is
  DERIVED from it. `photo_sha = sha256(image_jpeg)`, always computed, never caller-supplied. Key also carries model
  id, gen-params digest, `PROMPT_VERSION`. FixtureBackend replays by the derived key; MetaBackend sends the same
  object. Thin positional `segment()`/`spark_json()` shims keep MEM-003 callers and tests working.
- Root problem (eval): the backend seam is a replay interface keyed by cache identity, not a call interface -- no
  channel for image bytes, prompt or schema (main plan D3, D5, Ledger "server-built prompts").
- Sub-decision 1 CHANGED: item 5 (CacheKey fix) FOLDS INTO S2.3 as new S2.3a ("ModelRequest + CacheKey derivation +
  atomic schema-valid-only write-through"); no separate earlier change. One writer, one edit of backend.py.
- Sub-decision 5 AMENDED: fixture keys = sha of the PROCESSED photo, derived inside `ModelRequest`. S3/S4 re-validate
  the client-returned photo with new `validate_processed()` (JPEG, no EXIF, long side <= 2048, never re-encodes).
  Evidence: re-encoding `fixtures/demo/photo.jpg` at q90 gave 4 shas over 4 rounds (3c2dd205b0c8, e78f1f3c7195,
  5883ccc72139, dc44c9204d87), reproduced by the main thread.
- Additions:
  - `find_loci` wall-clock deadline ~90 s: phrases still pending = no boxes; skip the re-ask when < 15 s remain.
  - `find_loci(..., on_progress=None)` callback (no-op default) so S2.4 can move to NDJSON streaming if measured
    `/loci` latency > ~10 s.
  - meta-mode `run_live` binds 127.0.0.1 only until the S7 passcode lands.
  - Upload read uses `request.stream()` with a running byte cap, never `request.body()`.
- Sub-decisions 2, 3, 4, 6, 7 unchanged.
- Dissent / residual cons: no per-phrase progress until measured; S2.3 grows ~0.5 day (estimate); SAM/Spark latency
  unmeasured, so deadline and worker numbers are guesses; B (client fan-out with HMAC phrase tokens) is viable but
  loses to A + streaming on every con.
